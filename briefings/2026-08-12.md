### Stealing Reasoning Traces from Proprietary LLM APIs

**Source:** Simon Willison's Weblog · **Published:** 2026-08-11 · **Read time:** ~5 min

**Elevator pitch:** Researchers proved that encrypted chain-of-thought blocks returned by Anthropic, OpenAI, and Google APIs can be replayed across sessions and users, then jailbroken to recover the original reasoning in plaintext.

**Opinion vs. fact:**
- [FACT] Anthropic, OpenAI, and Google return encrypted chain-of-thought blocks to API clients; these blocks can be replayed across sessions, users, and models within a provider's ecosystem.
- [FACT] The researchers replayed a frontier model's trace into a weaker sibling model, jailbroke the weaker model, and recovered the stronger model's hidden reasoning as plaintext.
- [FACT] The paper was published on arXiv (2608.09867) in August 2026 and includes appendix examples of recovered traces.
- [FACT] In February 2026 Anthropic accused DeepSeek and others of large-scale distillation campaigns that allegedly used similar mechanisms.
- [OPINION] The architectural choice of returning encrypted traces client-side (rather than storing them server-side) creates a replayability vulnerability that providers should revisit.

**References:** arXiv:2608.09867, "Stealing Reasoning Traces from Proprietary LLM APIs." Paper hosted at stolen-thoughts.com. Simon Willison's blog post links to the paper and the demonstration curl command.

**Justifications:** The strongest evidence is the working exploit — a reproducible attack chain with results shown in the appendix. The vulnerability is not speculative; it follows directly from the providers' API architecture. The weakest aspect is that the paper does not detail what remediation providers have available short of changing their CoT architecture entirely.

**Core points:**
- Encrypted CoT blocks from Anthropic, OpenAI, and Google are interchangeable across sessions and users within a provider's ecosystem — this is an architectural property, not an implementation bug.
- Attack chain: obtain a frontier model's encrypted trace → replay into a weaker sibling → jailbreak the weaker model → recover plaintext reasoning.
- The same mechanism Anthropic alleged DeepSeek used for distillation campaigns is now a documented, reproducible public exploit.
- The vulnerability is in the client-side encrypted trace design; remediation likely requires changes to how providers expose and validate CoT blocks.

**Impact:** For architects building multi-component pipelines on top of Anthropic, OpenAI, or Google's reasoning APIs: encrypted reasoning traces are not confidential once they land in client code. Any trace you receive can be decoded. If you're routing traces between services — caching, logging, or passing them through proxies — treat them as cleartext reasoning. More broadly, this is likely to trigger provider API changes; monitor for breaking changes to how CoT blocks are returned and validated. It also validates concern about LLM distillation at scale and may accelerate provider-side changes to reasoning trace handling.

### TDD inside the agent loop — theater or actual value?

**Source:** Martin Fowler (Birgitta Böckeler, Thoughtworks) · **Published:** 2026-08-11 · **Read time:** ~8 min

**Elevator pitch:** An empirical experiment at Thoughtworks found that prompting coding agents to follow TDD inside their own loop does not reliably reproduce the quality benefits TDD gives human developers.

**Opinion vs. fact:**
- [FACT] Böckeler conducted a small, informal evaluation comparing agent-generated code quality with and without TDD prompting.
- [OPINION] An agent experiences no friction when writing tests first — it can write a test the same instant it plans the implementation — so the forcing-function benefit of TDD is absent.
- [OPINION] Without a human checkpoint between test and implementation, the requirement-thinking benefit of TDD is lost.
- [OPINION] The thinking-through-requirements benefit theoretically shifts upstream to spec-writing, but there is no TDD-like small-step mechanism at that layer.

**References:** Part of Böckeler's "Exploring Generative AI" series on martinfowler.com. Related to broader Thoughtworks work on harness engineering, feedback sensors, and coding agent infrastructure published in 2026.

**Justifications:** The conceptual argument is the strongest part: TDD's primary value for humans is the friction that forces careful requirement thinking at each small step, not the mechanical test-first sequence. That friction is definitionally absent when the agent controls both test and implementation simultaneously. The weakest aspect is scale — this is explicitly an informal small experiment, not a controlled study with statistical power.

**Core points:**
- TDD prompting in an agent loop does not replicate the human benefit because the agent doesn't experience the forcing function that makes TDD useful.
- The agent writes test and implementation near-simultaneously, eliminating the checkpoint between them.
- Benefit may shift to spec-writing, but no agent-native equivalent of TDD's small-step discipline exists at that layer yet.
- Cargo-culting human software practices into agent harnesses does not automatically transfer value.

**Impact:** Directly actionable for anyone designing agentic coding workflows. The takeaway is not "never use TDD with agents" but rather: validate whether TDD instructions actually improve your agent's output in your specific context before making it a team standard. The framing suggests that agent-native quality practices — harness engineering, feedback sensors, linting and tests wired into the loop — may deliver more reliable improvement than prompting agents to mimic human workflows. Worth reviewing your current agent scaffolding with this lens before adding TDD to your standard prompt library.
