**Justification:** The 6.6% → 82.3% improvement is striking, but the baseline matters — improvement over an untrained team on a specifically designed cooperative task is an easier bar than improvement over a well-prompted frontier model. The ~$20 reproduction cost and the open TRL recipe are the practically significant claims; they make the experiment independently verifiable.

**Core points:**
- Four 0.6B agents trained with group reward on a verifiable sorting task; team wins when any agent submits the correct answer
- Task success rises from 6.6% to 82.3%; tokens per attempt down 37% vs. untrained baseline
- Equal-token-budget comparison is the methodologically honest framing for production cost analysis
- Full training recipe on TRL; reproducible at ~$20 on commodity H100s

**Impact:** A reproducible, cheap training recipe for small cooperative multi-agent systems is directly useful for architects evaluating whether to train specialist sub-agents versus prompting a frontier model for orchestration. The equal-token-budget framing is the right mental model for cost-benefit analysis in production agent architectures. For OSS platforms where inference cost is a real constraint, trained small-model swarms may be a viable alternative to frontier model calls for well-scoped subtasks.

- [FACT] Clay uses BullMQ for job queuing.

- [FACT] Per-row agent execution makes inference spiky: a 50,000-company run hits providers simultaneously.
- [FACT] Clay implemented throttling, pause-and-resume on provider failures, and fair scheduling to prevent large jobs starving smaller ones.
- [OPINION] Barg says agents still cannot reliably diagnose their own traces, so many skills are still written by hand.
- [OPINION] Frontier models are more valuable for orchestration and deep research; cheaper open-weight models are preferred for structured sub-tasks.

**References:** Jeff Barg (Head of AI, Clay). LangSmith, BullMQ, Pi harness, Claude Code mentioned.

**Justification:** The eval evolution story — from tool-call checking to trajectory and property evaluation — is consistent with what the broader AI engineering community reports from production deployments. The burst-inference problem at 50k rows is a specific, described production failure mode; the mitigations (throttling, fair scheduling) are actionable. The concern about BullMQ at 10x scale is an acknowledged uncertainty, not a failure — most production agent architectures face similar unknowns.

**Core points:**
- Sculptor rebuilt from tool-loop to coding agent; runs the Clay CLI in a cloud sandbox via the Pi harness
- Early evals checked tool call names; now evals check trajectory and whether the built workflow has the properties the user asked for
- 50k-row runs create burst inference demand; mitigated with throttling, pause-on-failure, and fair scheduling
- BullMQ unvalidated at 10x current load — acknowledged as a known production risk

**Impact:** The eval maturation story — from "what tools were called" to "does the output have the right properties" — is the most transferable lesson here. This is the right eval design for any agentic workflow that produces structured artifacts rather than conversational output. The burst-inference problem is a production pattern that any OSS platform architect building agent workflows at scale will hit; the solution (fair scheduling plus provider-level throttling with resume) is deployable with standard queuing infrastructure.
