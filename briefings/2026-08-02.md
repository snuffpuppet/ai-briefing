### 2. MCP 2.0: Stateless protocol eliminates session management

**Source:** Simon Willison's Weblog · **Published:** 2026-07-31 · **Read time:** ~8 min

**Elevator pitch:** The 2026-07-28 MCP specification transforms the Model Context Protocol from a stateful bidirectional session protocol into a stateless request/response protocol, enabling deployment on standard load balancers and decoupling client and server lifecycles.

**Opinion vs. fact**
- [FACT] The 2026-07-28 MCP spec removes protocol-level sessions, the initialize/initialized handshake, and the Mcp-Session-Id header
- [FACT] Every request now carries protocol version and client capabilities in `_meta` (io.modelcontextprotocol/protocolVersion, io.modelcontextprotocol/clientCapabilities)
- [FACT] Mcp-Method and Mcp-Name HTTP headers are now required on Streamable HTTP POST requests
- [FACT] tools/list, resources/list, prompts/list, resources/read, and resources/templates/list responses now require ttlMs and cacheScope fields
- [FACT] A new Tasks extension (io.modelcontextprotocol/tasks) handles long-running operations with tasks/get, tasks/update, tasks/cancel
- [FACT] When a tool needs mid-call user input, the server returns resultType: "input_required"; client retries with answers in inputResponses (Multi Round-Trip Request pattern)
- [FACT] Roots, Sampling, and Logging features are deprecated with a 12-month transition window
- [FACT] TypeScript, Python, Go, and C# SDKs have beta support for the new spec
- [FACT] Authorization updated to RFC 9207 issuer validation; Client ID Metadata Documents replace Dynamic Client Registration
- [OPINION] "The most significant change to MCP since it first launched" (Simon Willison)
- [OPINION] Stateless MCP returns the protocol to web-native patterns, making it substantially more deployable

**References:** MCP specification blog (blog.modelcontextprotocol.io); official MCP changelog (modelcontextprotocol.io/specification/2026-07-28/changelog); Simon Willison; MCP SDK documentation

**Justifications:** The specification changes are documented in the official MCP blog, which was accessible. The deployability benefits follow structurally from eliminating session state — any architect familiar with stateless HTTP can verify the claim. The "most significant change" framing is opinion but well-grounded by the scope of structural changes. The weakest claim would be any projection about adoption timeline or ecosystem convergence.

**Core points**
- Stateless by default: no sticky sessions, no shared state stores — MCP servers can be deployed as standard stateless HTTP services behind any round-robin load balancer
- Header-based routing: Mcp-Method and Mcp-Name headers allow gateways and WAFs to route, meter, and enforce policy on MCP traffic without parsing JSON bodies
- List response caching: ttlMs and cacheScope on tool/resource lists reduce polling overhead in multi-agent systems with many concurrent clients
- Multi Round-Trip Requests: replaces server-initiated mid-call streams with a cleaner poll-based retry pattern
- Authorization hardening: credentials are now bound to issuer, preventing cross-server credential reuse; authorization server SHOULD include RFC 9207 iss in responses

**Impact:** For anyone building or evaluating MCP-integrated systems: stateless MCP removes a meaningful deployment blocker. The old stateful protocol required either single-instance servers or a distributed session store; a pool of identical stateless replicas now handles any request. For OSS/BSS tooling where HA and horizontal scale are baseline requirements, this matters. The header-based routing addition is the underappreciated win — standard API gateway patterns (rate limiting, auth enforcement, traffic shaping) now apply to MCP endpoints without touching server code. The caching TTL hints reduce unnecessary polling overhead in systems with many agents querying the same tool registries. Anyone building new MCP server implementations should start from the 2026-07-28 spec, not prior versions.
